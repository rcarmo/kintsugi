# Kintsugi v0.4.15

Not published: CI dependency-download delays exhausted the verification budget. These changes are included in [v0.4.16](v0.4.16.md).

Removes unintended systemd task ceilings inside workspaces while preserving finite container and installation PID budgets.

## Task limits

Systemd normally limits a service or scope to 15% of the container task budget. With a 1024-task container limit, Kintsugi's tmux service and init.scope inherited a 153-task ceiling. Go and other threaded workloads could therefore fail with errno=11 while the container still had capacity.

The workspace image now supplies a manager drop-in with `DefaultTasksMax=infinity` and explicitly sets `TasksMax=infinity` for Kintsugi runtime services. Helper, Docker and containerd already had that setting; tmux, initialisation and gateway now do too. This removes internal default ceilings; container `pids.max`, ancestor limits, memory/CPU boundaries and OOM safeguards remain unchanged.

## Verification

Disposable Linux/systemd fixtures reproduced the old limit: direct commands created 151 of 160 requested threads, and tmux workloads 150, despite a 1024-task root budget. With the new configuration, both created all 160 threads under a smaller 256-task root budget. With a 128-task root budget, both were correctly refused at that boundary.

Local verification passed **2,719 tests**, with **36 skipped** and **zero failures**, plus frozen install, lint, TypeScript, image packaging and content-identity checks. Native publication also checks the manager drop-in and service settings in each shipped architecture. No live workspace limits were changed during verification.

## Upgrading workspaces

First update the Kintsugi installation to **v0.4.15**, using the `latest` channel or an explicit version pin. `stable` remains v0.4.10. New workspaces using the updated default image receive the fix. Custom images pinned to an older base need rebuilding or the in-place repair below.

An app update does not replace existing workspace images. **Park/unpark alone does not add the new configuration to an old image.** Existing workspaces can be repaired without recreation:

1. Save your work and stop important jobs. Back up data before maintenance. Do not use this recipe to override intentional task limits you configured separately.
2. In that workspace's **Terminal**, run:

```sh
sudo sh <<'SH'
set -eu
install -d /etc/systemd/system.conf.d
printf '[Manager]\nDefaultTasksMax=infinity\n' > /etc/systemd/system.conf.d/90-kintsugi-workspace-limits.conf
for unit in kintsugi-tmux.service kintsugi-init.service kintsugi-gateway.service kintsugi-helper.service docker.service containerd.service; do
  install -d "/etc/systemd/system/$unit.d"
  printf '[Service]\nTasksMax=infinity\n' > "/etc/systemd/system/$unit.d/90-kintsugi-task-budget.conf"
done
SH
```

3. **Park, then unpark that workspace** in Kintsugi. This restarts its processes so PID 1 reads the persistent manager defaults. Workspaces' existing files and Docker stores are retained; this is a configuration repair, not an OS/image replacement.
4. Check inside the workspace:

```sh
systemctl show -p DefaultTasksMax
systemctl show kintsugi-tmux.service init.scope -p Id -p TasksMax
cat /sys/fs/cgroup/pids.max
```

The manager and service/scope task settings should report `infinity`; root `pids.max` should remain your configured finite budget, normally `1024`. If intentional later overrides remain, inspect them rather than deleting them blindly. `systemd-analyze cat-config systemd/system.conf` and `systemctl cat kintsugi-tmux.service` show the relevant configuration.

If the tmux cap prevents opening a Terminal, use the **Host** root terminal to enter the correct container with `docker exec --user root kintsugi-<workspace-id> sh`, then run the block's contents without `sudo`. If the entire container is exhausted, park/unpark first to stop its jobs before repairing it. An OOM-blocked workspace still requires the existing explicit recovery/cooldown; this release does not bypass that guard.

The in-place recipe was tested against an old disposable image: the same container/image retained a workspace-file sentinel after restart, both internal limits became unlimited, 160-thread probes passed, and the root budget stayed 1024. No real user workspace was upgraded or restarted.

No dependency, runtime-image pin, compatibility-counter or persisted-format changes. Fork safeguards and attribution remain unchanged. Pre-existing local resource-default edits are excluded.

Publication advances `latest` only. No existing installation is updated or restarted by publication.
