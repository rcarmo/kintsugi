# Kintsugi v0.5.3

## Changes

- Restore WebSockets for the main live-update channel. Updates and subscription commands now share one connection; remove the SSE transport and separate command POSTs.
- Preserve subscription recovery, fresh snapshots after reconnect, heartbeats, ordered command batches, Origin checks and delivery limits.
- Keep workspace applications' own SSE streams, settings access events, direct external assets and opaque preview isolation unchanged.

## Updating

Reload any tabs opened before the update: the old SSE client cannot connect to the new WebSocket-only channel. HTTPS connections use `wss://` on the existing management authority; no extra public port or new configuration is required.

No persisted-state format, dependency, runtime-image pin or compatibility-counter changes. System capability remains 4; the app minimum remains 0. Publication advances `latest` only and does not update or restart an installation. `stable` is unchanged.

## Verification

Frozen dependency installs, typecheck, asset build, System bundle build and workflow validation passed locally. The full local suite passed 2,890 tests with 36 skips and no failures across 403 serial batches, including the targeted app/proxy protocol checks. The running app passed Chromium and Linux WebKit checks through diagnostic TLS termination for live updates, reconnect, offline recovery, reload and heartbeats, with no Cable command POSTs. Diagnostic certificate checks were bypassed and service workers were blocked in those browser contexts; these checks do not establish genuine Safari or certificate trust acceptance. Tagged publication also requires full CI and both native image/packaged boot gates.

## Known limitations

Existing preview-browser storage limitations remain: independent views do not share live IndexedDB transactions/auto-increment, and forced unacknowledged closure of the last WebKit preview can lose recent writes. Opaque previews do not support native service-worker registration or cross-sandbox DOM access. Genuine macOS Safari/certificate trust acceptance remains unverified.
